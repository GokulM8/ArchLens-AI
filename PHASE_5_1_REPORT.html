Problem Statement

Phase 5 baseline analysis produced:

  • 48 recommendations total
  • 46 HIGH priority (95.8%)
  • 10 exact duplicates (same type, same component)
  • 27 weak signals (single evidence type, no supporting signals)
  • 15 components with 3+ recommendation types each

The distribution suggested that the engine was:

  • Over-generating opportunities from correlated signals
  • Treating architectural observations as refactoring tasks
  • Assigning HIGH priority too aggressively
  • Creating duplicates from redundant detection logic

Changes Implemented

1. Layer Violation Deduplication

Change: Group violations by source component instead of creating one recommendation per violation.

Additional improvement: Filter expected architectural patterns (e.g., routes → services, services → database). These are normal layered architecture, not violations.

Expected patterns skipped: • Presentation → Application (routes → services) • Presentation → Domain (routes → models) • Application → Data (services → repos) • Application → Infrastructure (services → config) • Application → Domain (services → models)

Result: 25 layer violations → 0-3 genuine violations reported

2. Centralization Rule Strengthened

Before: High in-degree alone triggers recommendation.

After: Require at least one supporting signal:

  • Component also has high coupling risk, OR
  • Component is large (>10 members), OR
  • Component shows extreme centrality (3x repository average)

Result: 10 centralization opportunities → 2 actionable recommendations

3. Coupling Rule Refined

Before: Coupling above average threshold triggers HIGH priority.

After: Require additional evidence:

  • Secondary architectural signals (size, role issues), OR
  • Extreme coupling (>3x repository average)

Special case: Utilities, configuration, and database components legitimately have high coupling. Skip these unless extreme.

Result: 11 coupling opportunities → 6 high-quality recommendations

4. Large Module Rule Tightened

Before: Modules with >10 members automatically flagged.

After: Require multiple signals:

  • Member count >15 (was >10)
  • At least 2 of: high LOC, mixed responsibilities, high coupling

Result: Eliminated weak single-signal recommendations

1. Signal-Based Filtering

Recommendations now require multiple independent signals before triggering. Single metrics alone are insufficient.

Evidence strength matters. Weak signals (path names, single metrics) are downgraded or filtered entirely.

3. Architectural Context

Legitimate architectural patterns (e.g., normal layered dependencies) are no longer flagged as violations.

4. Component Role Awareness

Components with legitimate high connectivity (utilities, config, database) are handled specially.

5. Priority Accuracy
